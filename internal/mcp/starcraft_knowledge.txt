"StarCraft: Remastered" is a real-time strategy game where players choose a race (Terran, Protoss or Zerg), build economies, form armies, sometimes ally other players, and battle for map control until one side destroys all opponent buildings to win.

Game Mechanics

- Economy: workers mine → resources → spend on units/buildings
- Tech tree: unlocks progressively with buildings
- Army control: composition, micro, positioning
- Fog of war: vision-limited
- Win condition: destroy all opponent buildings
- Maximum supply count: 200. Workers cost 1. Heavier units cost 2, 4, etc.

Units: combat, workers, spellcasters, transports, detectors
Resources: minerals, vespene gas, supply (food cap)
Buildings: tech tree enablers, production, economy, defense
Worker units: Drone (Zerg), Probe (Protoss), SCV (Terran)
Main building: Nexus (Protoss), Command Center (Terran), Hatchery/Lair/Hive (Zerg). Resources are gathered to these buildings.

Replay Essentials

- Timeline of actions (build orders, expansions, engagements)
- APM (actions per minute), supply, resources, spending efficiency
- Army composition over time
- Map size is in tiles (128x128, 96x256) but (x, y) is in pixels. 1 tile = 32 pixels.
- Map control, scouting, expansions

Meta terms

- "rush": attacking an opponent within a few minutes of game start.
- "timing push": deliberate attack launched at a specific moment when a build order hits a temporary power spike (e.g. first tanks with siege, zealots become fast, mutalisks get +1 attack).
- "tech switch": rapidly shifting production to a different unit tech path to exploit an opponent's weak counters (e.g. mutalisks → lurkers, marine+medic → tank+goliath).
- "natural": the first expansion (main building) to gather more resources, in close proximity to the main starting location.
- "expa/expansion": another expansion which is not necessarily the natural.
- Main building starting locations are usually conveyed in o'clock positions (like 3, 6, 9, 12).

How screpdb models a replay

screpdb reads a folder of replay files into memory and runs pattern detection
on each one. What it keeps per game, and what you read over the JSON API, is:

- The game: map, matchup, duration, engine, lobby kind, game source, map kind
  (Regular, Money, UseMapSettings), and the map's base layout.
- The players: name, race, team, APM and eAPM, start location, winner flag,
  observer flag, human/computer type, hotkey usage and viewport activity.
- The production stream: every Build, Train, unit morph, building morph, Tech,
  Upgrade and composition-relevant spell cast, with the second it happened.
  This is what build orders, timings and army composition are derived from.
- Chat lines, alliance topology over time, and the derived markers and game
  events below.

There is NO raw command stream. Right-clicks, move orders, unit tags and screen
coordinates are parsed and used during detection, then dropped. Questions that
need individual micro actions cannot be answered from this API — say so rather
than inventing an answer.

Derived analysis: markers and game events

screpdb does not just store what happened; it runs pattern detection and stores
the verdicts. There are two kinds, and list_marker_definitions returns the live
vocabulary of both with their labels.

- Markers: one per (game, player). The most important are BUILD-ORDER OPENERS,
  whose feature keys are prefixed "bo_", describing the first ~2 minutes of
  macro — e.g. bo_9_pool, bo_12_hatch, bo_2_gate, bo_gate_expand,
  bo_1_gate_core, bo_t_111 (Terran 1-1-1), bo_cc_first, bo_forge_expa. Openers
  that could not be resolved to a named build use opener_unresolved, *_fuzzy or
  bo_*_other; treat those as "unknown", not as a build. Other markers capture
  timings and behaviours (e.g. never_used_hotkeys, viewport_multitasking,
  never_upgraded), and many carry the measured seconds behind the verdict.
- Game events: narrative moments during a game — rushes (cannon_rush,
  bunker_rush, zergling_rush), drops, nydus attacks, proxies (e.g.
  proxy_starport), mind control, scouting and expansions. Each has a second, an
  acting player, often a target player, and a map location expressed as a base
  (starting / natural / expansion) and an o'clock position.

The bo_ prefix is only a loose hint about race: bo_p_*/bo_t_* are reliably
Protoss/Terran, but many Zerg openers are just bo_9_pool/bo_12_hatch with no
race letter. Read the player's race from the response rather than inferring it
from the key.

Report metrics

- Stick to human players; skip computers and observers.
- The winner flag is not fully reliable: players may leave after winning, and
  replays may be incomplete.
- Useful per-player signals the API already computes: APM and eAPM, hotkey
  usage and hotkey signature, unit-production cadence, viewport multitasking,
  build-order openers and their expert timing deltas.
- Better players tend to have higher APM, use hotkeys, and convert a bigger
  worker count into more units and buildings.
- Build-order names ("2 Hatch Muta", "1 Gate Expand") are the canonical way to
  describe an opening; prefer the stored marker over reconstructing one.

Answering questions

- Start with get_api_schema, then list_top_players or /api/games to see what is
  actually in this corpus.
- The corpus is one user's replay folder, capped at its newest games. Do not
  generalise from it to StarCraft as a whole, and say how many games a claim
  rests on.
- /api/games/{replayID} returns the whole game report in one response: players,
  build orders, timings, events, chat. Reach for it before assembling an answer
  from several endpoints.
